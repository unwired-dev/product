# Gate incoming attachment downloads in message presentation

Incoming attachments use a provider-neutral descriptor and download operation. A message presentation may start that operation only through the device-local attachment policy: On Demand requires an explicit user action, Wi-Fi starts automatically on Wi-Fi or wired networking, and Always starts automatically on any available network. Policy or network changes and presentation dismissal cancel the presentation-scoped task. Failures keep the message readable and offer a retry.

Gmail is the first provider implementation because its explicit body read already returns the full MIME tree and its authenticated attachment endpoint is independently callable. Ordinary attachment-disposition parts and filename-bearing non-inline parts are exposed; each Inline Image remains part of the isolated message presentation instead. Gmail may include small attachment bytes in that required MIME response before a per-attachment decision is possible; the full response is capped at 40 MB, those bytes stay presentation-scoped, and the Bounded Encrypted Body Cache stores only their descriptors. Legacy cache entries that lack Attachment Preview metadata are refreshed. Standards-Based Mailbox Connections use SwiftMail's UID-validity-checked MIME structure and part-fetch APIs to derive the same provider-neutral descriptors, exclude each Inline Image and readable body part, and download only the matching numeric MIME section. The SwiftMail boundary limits the declared and received transfer-encoded part before decoding and validates the decoded result against the 25 MB policy; transfer-encoded `BODYSTRUCTURE` octets are not treated as decoded attachment bytes. Their Bounded Encrypted Body Cache payload retains descriptors but no attachment bytes. `IMAPMailboxConnectionAdapter` owns the provider-neutral Attachment Preview and Downloaded Attachment policy in Apple Swift while SwiftMail owns IMAP framing, MIME parsing, and transfer decoding; no TypeScript layer participates. Exchange Web Services exposes no descriptors until its adapter implements the same boundary, so it has no attachment request path that can bypass the gate.

Microsoft Graph reads attachment metadata separately without requesting `contentBytes`, classifies inline file attachments and unsupported item or reference attachments inside the provider adapter, and exposes only ordinary file attachments through the provider-neutral descriptor. Descriptor failures do not hide otherwise readable message text and remain retryable. Resolved descriptors are stored with the text in the encrypted body cache, while downloaded `$value` bytes remain outside that cache and are read through the same authenticated size boundary. Immutable Graph message IDs and provider attachment IDs form the stable download identity across folder moves and refreshes.

Downloads are limited to 25 MB, validated against provider-declared size when present, and bounded while reading the authenticated endpoint response rather than after an unbounded buffer. Each Downloaded Attachment is saved under opaque connection, message, and part digests in Application Support with complete file protection. The store is capped at 250 MB with oldest-file eviction and is cleared with the owning Mailbox Connection or Product Account. The original filename is reduced to its final path component. Downloaded Attachment bytes remain device-local and never enter the Bounded Encrypted Body Cache or Product Sync.

The reader derives preview availability only for passive image, PDF, plain-text, audio, and video types. Image and PDF thumbnails are generated in memory from the protected local file, and tapping either a thumbnail or the Quick Look action presents that same file through the system preview. Preview access refreshes the stored file's modification date so the existing 250 MB eviction policy treats recently previewed content as recently used. The app creates no separate plaintext or synchronized preview cache; unsupported types retain the explicit Share / Open path.
