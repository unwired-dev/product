# Gate incoming attachment downloads in message presentation

Incoming attachments use a provider-neutral descriptor and download operation. A message presentation may start that operation only through the device-local attachment policy: On Demand requires an explicit user action, Wi-Fi starts automatically on Wi-Fi or wired networking, and Always starts automatically on any available network. Policy or network changes and presentation dismissal cancel the presentation-scoped task. Failures keep the message readable and offer a retry.

Gmail is the first provider implementation because its explicit body read already returns the full MIME tree and its authenticated attachment endpoint is independently callable. Ordinary attachment-disposition parts and filename-bearing non-inline parts are exposed; inline Content-ID images remain part of the isolated message presentation instead. Gmail may include small attachment bytes in that required MIME response before a per-attachment decision is possible; the full response is capped at 40 MB, those bytes stay presentation-scoped, and the encrypted body cache stores only their descriptors. Legacy cache entries that lack attachment metadata are refreshed. Other providers expose no descriptors until their adapters implement the same boundary, so they have no attachment request path that can bypass the gate.

Calendar invitations use a narrower provider-part boundary. Metadata synchronization may retain only the calendar MIME type, provider part and attachment identifiers, transfer encoding, declared size, and an opaque dismissal identifier. It never selects part body data. An explicit Add to Calendar action may download that part through the authenticated provider operation; automatic body prefetch and ordinary attachment policy do not initiate the invitation read. Gmail caps its attachment endpoint or bounded inline-part response at 1 MB while receiving and decoding it. Standards-Based Mail uses SwiftMail BODYSTRUCTURE metadata to reject parts declared above 1 MB, selects exactly one supported calendar part, fetches only that IMAP section after the action, and rejects a decoded result above the same limit.

Microsoft Graph reads attachment metadata separately without requesting `contentBytes`, classifies inline file attachments and unsupported item or reference attachments inside the provider adapter, and exposes only ordinary file attachments through the provider-neutral descriptor. Descriptor failures do not hide otherwise readable message text and remain retryable. Resolved descriptors are stored with the text in the encrypted body cache, while downloaded `$value` bytes remain outside that cache and are read through the same authenticated size boundary. Immutable Graph message IDs and provider attachment IDs form the stable download identity across folder moves and refreshes.

Exchange Web Services reads `item:Attachments` metadata separately from attachment content, keeps item attachments and inline or Content-ID file resources provider-local, and exposes only ordinary file attachments. The encrypted EWS body cache stores the resolved descriptors with readable text and refreshes legacy text-only entries when metadata reports attachments. Each public descriptor combines the owning immutable EWS message identity with the provider attachment ID so a descriptor cannot be replayed against another message. `GetAttachment` remains device-authenticated and bounds the base64 SOAP response while receiving it, then validates the decoded bytes against both the provider-declared size and the shared 25 MB limit. The downloaded bytes enter only the existing protected attachment store.

Standards-Based Mail derives ordinary attachment descriptors from SwiftMail BODYSTRUCTURE metadata without selecting part bytes. Readable body parts and inline Content-ID resources stay out of that list, while the locally persisted descriptor retains only the filename, MIME type, transfer encoding, declared size, and part selector. The reader revalidates all descriptor fields against the current owning message before fetching exactly that decoded IMAP section. Both the declared size and the streamed and decoded response remain bounded by the shared 25 MB limit before bytes can enter the protected attachment store.

Downloads are limited to 25 MB, validated against provider-declared size when present, and bounded while reading the authenticated endpoint response rather than after an unbounded buffer. Successful downloads are saved under opaque connection, message, and part digests in Application Support with complete file protection. The store is capped at 250 MB with oldest-file eviction and is cleared with the owning Mailbox Connection or Product Account. The original filename is reduced to its final path component. Downloaded bytes remain device-local and never enter the encrypted message-body cache or Product Sync.

The reader derives preview availability only for passive image, PDF, plain-text, audio, and video types. Image and PDF thumbnails are generated in memory from the protected local file, and tapping either a thumbnail or the Quick Look action presents that same file through the system preview. Preview access refreshes the stored file's modification date so the existing 250 MB eviction policy treats recently previewed content as recently used. The app creates no separate plaintext or synchronized preview cache; unsupported types retain the explicit Share / Open path.
