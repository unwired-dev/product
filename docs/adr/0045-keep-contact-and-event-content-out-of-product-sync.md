# Keep contact and event content out of Product Sync

The Apple client owns Add to Contacts and Add to Calendar extraction, permission requests, review, Contacts and Calendar reads, and operating-system writes. It detects a Contact Candidate only from the name and email address in message headers for People-classified direct correspondence with reply evidence; a body already available locally may add fields but cannot establish candidacy, and detection never fetches a missing body. Independently, it detects a Calendar Event Candidate from a structured calendar invitation or, in the later prose-detection increment, from an unambiguous date and time in a body already available locally. Detected fields, Apple Contacts contents, Calendar contents, and calendar-event mappings remain device-local and do not enter Product Sync. For Contact Candidate and Calendar Event Candidate workflows, the TypeScript backend may transport only opaque encrypted **Feature Suggestion Preference** data, with one separate synchronized preference for each proactive feature, plus type-level suppressions and opaque feature-level dismissal identifiers through End-to-End Encrypted Product Sync. Those identifiers cannot identify messages, senders, contacts, calendar events, operating-system records, extracted fields, or candidates; the backend never stores extracted fields or operating-system records.

Contacts and Calendar remain authoritative for committed records. The client requests each operating-system permission only when the user acts, requires review before creating, merging, updating, or removing data, never overwrites a non-empty Contact field automatically, and checks iCalendar identity before adding or updating a structured event.

The Gmail structured-event increment detects supported calendar MIME parts from metadata alone. Its explicit action downloads at most 1 MB, accepts one bounded `VEVENT`, rejects recurrence and ambiguous floating times, and recognizes request and cancellation changes through iCalendar UID, sequence, and a content fingerprint. EventKit access is requested only after that action. A device-local opaque-UID mapping selects Already Added, reviewed Update, reviewed Removal, or Already Removed; no silent Calendar mutation occurs. Calendar Event has presentation priority over Unsubscribe and Contact so an expanded message shows at most one proactive card.

The Microsoft Graph structured-event increment keeps the same boundary. Message delta responses expand attachment metadata without `contentBytes` and recognize structured request and cancellation event-message types. An explicit action either retrieves one matching calendar attachment through the existing 1 MB authenticated attachment boundary or expands the event message's minimal associated-event fields in UTC. The client rejects recurrence and ambiguous time zones, uses Graph's iCalendar UID and last-modified ordering for reviewed updates and cancellations, and keeps all resulting event values and mappings device-local.

The Exchange Web Services structured-event increment also keeps that boundary. Metadata pages recognize meeting requests and cancellations by their EWS item shape and batch-load only attachment descriptors for messages that advertise attachments; neither path requests a message body, MIME stream, or attachment content. An explicit action revalidates the current owning item and either retrieves one matching calendar file through the existing authenticated 1 MB attachment boundary or requests only the structured UID, time, location, cancellation, recurrence, and last-modified fields. EWS UID and last-modified ordering preserve reviewed update and cancellation continuity when provider item and change-key identities refresh, while all event values and mappings remain device-local.
