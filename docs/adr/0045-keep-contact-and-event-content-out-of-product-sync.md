# Keep contact and event content out of Product Sync

The Apple client owns Add to Contacts and Add to Calendar extraction, permission requests, review, Contacts and Calendar reads, and operating-system writes. It detects a Contact Candidate only from the name and email address in message headers for People-classified direct correspondence with same-connection reply or repeated-correspondence evidence; a body already available locally may add fields but cannot establish candidacy, and detection never fetches a missing body. Independently, it detects a Calendar Event Candidate from a structured calendar invitation or, in the later prose-detection increment, from an unambiguous date and time in a body already available locally. Detected fields, Apple Contacts contents, Calendar contents, and calendar-event mappings remain device-local and do not enter Product Sync. For Contact Candidate and Calendar Event Candidate workflows, the TypeScript backend may transport only opaque encrypted **Feature Suggestion Preference** data, with one separate synchronized preference for each proactive feature, plus type-level suppressions and opaque feature-level dismissal identifiers through End-to-End Encrypted Product Sync. Those identifiers cannot identify messages, senders, contacts, calendar events, operating-system records, extracted fields, or candidates; the backend never stores extracted fields or operating-system records.

Contacts and Calendar remain authoritative for committed records. The client requests each operating-system permission only when the user acts, requires review before creating, merging, updating, or removing data, never overwrites a non-empty Contact field automatically, and checks iCalendar identity before adding or updating a structured event.

The Gmail Contact Candidate increment accepts exactly one normalized sender identity whose Reply-To, when present, resolves to the same address; aliases, mailing lists, automated mailboxes, and multi-recipient messages do not qualify. A sent message in the same Mailbox Connection and Thread provides reply evidence, while two messages from the same correspondent provide repeated-correspondence evidence. Only a bounded signature marker in a body already held by the reader may add explicitly labeled organization or address fields, a phone number, or an HTTPS URL. The explicit Add action requests Contacts access, checks email and phone duplicates, and passes the candidate to the native Contacts create-or-merge review. A 30-day dismissal is keyed by an opaque digest of meaningful fields and evidence, so newly available contact fields or stronger correspondence evidence can present a refreshed candidate without synchronizing those values.

The Gmail and Standards-Based Mail structured-event increments detect supported calendar MIME parts from metadata alone. Their explicit action downloads at most 1 MB, accepts one bounded `VEVENT`, rejects recurrence and ambiguous floating times, and recognizes request and cancellation changes through iCalendar UID, sequence, and a content fingerprint. Standards-Based Mail obtains the part selector, transfer encoding, MIME type, and declared size from IMAP BODYSTRUCTURE without fetching body bytes. EventKit access is requested only after the explicit action. A device-local opaque-UID mapping selects Already Added, reviewed Update, reviewed Removal, or Already Removed; no silent Calendar mutation occurs. Calendar Event has presentation priority over Unsubscribe and Contact so an expanded message shows at most one proactive card.

The provider-neutral prose-event increment runs off the main actor only after the owning message body has already loaded. It rejects bodies above its scan limit rather than truncating them and offers a candidate only when the body contains exactly one unambiguous explicit calendar date—using a month name or ISO `yyyy-mm-dd`—with an explicit time. It keeps the event fields and stable fingerprint in memory or device-local storage and derives only an opaque dismissal identifier for Product Sync. Every prose candidate opens the native Calendar editor without requiring full Calendar access because time zone, duration, and location may need correction. A product-account-wide local fingerprint match produces a duplicate warning and a fresh editor; it never selects, updates, or removes an event identified by an iCalendar UID. Structured invitation reads and updates retain their full Calendar access requirement.

The Microsoft Graph structured-event increment keeps the same boundary. Message delta responses expand attachment metadata without `contentBytes` and recognize structured request and cancellation event-message types. An explicit action either retrieves one matching calendar attachment through the existing 1 MB authenticated attachment boundary or expands the event message's minimal associated-event fields in UTC. The client rejects recurrence and ambiguous time zones, uses Graph's iCalendar UID and last-modified ordering for reviewed updates and cancellations, and keeps all resulting event values and mappings device-local.

The On-Premises Exchange Connection structured-event flow also keeps that boundary and produces a Calendar Event Candidate. Metadata pages recognize `MeetingRequest` and `MeetingCancellation` items, plus equivalent `item:ItemClass` values on message items, and batch-load only attachment descriptors for messages whose `item:HasAttachments` metadata is true; these predicates do not request a message body, MIME stream, or attachment content. An explicit action uses Stable Provider Message Identity to locate and revalidate the current owning item, including recovery when item or change-key identities refresh, and either retrieves one matching calendar file through the existing authenticated 1 MB attachment boundary or requests only the structured UID, time, location, cancellation, recurrence, and appointment sequence number fields. EWS UID and appointment sequence ordering preserve reviewed event-revision and cancellation continuity, while all Calendar Event Candidate values and mappings remain device-local.
