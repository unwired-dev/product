# Device-held mail provider tokens with push relay

The product needs push and sync behavior but should keep mail provider OAuth tokens on trusted user devices for v1. The backend may receive minimal mailbox-change metadata from provider push systems and route wakeups to devices through APNs, but it must not fetch mail, hold provider tokens, read message bodies, read categories, or perform classification. This preserves the privacy boundary while accepting more complex client-side sync, watch renewal, and background execution constraints.

For Gmail connection, trusted devices persist provider OAuth credentials locally and register only Operational Account Data with the backend: an opaque Mailbox Connection identifier, provider name, trusted device, and connection verification timestamps. Gmail account identifiers and email addresses remain inside the end-to-end encrypted Mailbox Connection definition and are not backend-readable. To route future Gmail pushes, a dedicated registration handler accepts the canonical Gmail address as a transient, non-logged input over the authenticated connection, derives an HMAC-SHA-256 digest with a backend-held, access-controlled routing key, and immediately discards the address; it stores only that versioned digest mapped to the opaque connection identifier and its trusted devices. The digest is not an account identifier or email address and cannot be used to recover one without the backend key. Routing-key rotation creates and routes both the current and prior versioned digests until all active registrations are renewed, then deletes the prior mappings; key material is restricted to the registration and push-routing service and is never returned to clients or logs. Gmail push payloads are the same narrow exception: Google supplies an email address and history identifier to the backend as transient Minimal Push Metadata; handlers derive the routing digest, route the wakeup, must not persist the payload values or include them in application logs, and discard them afterward. When a Mailbox Connection is removed from all trusted devices, the backend atomically disables and deletes its digest mapping before removing device authorization, invalidates queued wakeups for that connection, and retains no digest tombstone. Backend APIs for Gmail connection status must not accept or return access tokens, refresh tokens, message bodies, categories, classification data, Gmail account identifiers, or email addresses.

The existing single-Gmail bootstrap implementation still stores and returns `emailAddress` and `providerAccountIdentifier` from `mailProviderConnections`, and persists Gmail push values in `gmailPushVerificationSignals`. That temporary implementation does not meet this ADR. The migration is a release gate: first block new legacy writes, then permit the legacy endpoint only for authenticated trusted-device migration. Each legacy row has a durable migration state and single-writer claim; idempotent retries persist the encrypted Mailbox Connection definition and verify its replacement digest route before atomically scrubbing the legacy row and every associated push-verification signal, so a crash or competing trusted device can safely resume from any state. The multi-connection connection-status API remains disabled until no legacy rows or signals remain; it then follows the boundary above.
