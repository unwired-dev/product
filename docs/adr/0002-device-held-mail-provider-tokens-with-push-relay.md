# Device-held mail provider tokens with push relay

The product needs push and sync behavior but should keep mail provider OAuth tokens on trusted user devices for v1. The backend may receive minimal mailbox-change metadata from provider push systems and route wakeups to devices through APNs, but it must not fetch mail, hold provider tokens, read message bodies, read categories, or perform classification. This preserves the privacy boundary while accepting more complex client-side sync, watch renewal, and background execution constraints.

For Gmail connection, trusted devices persist provider OAuth credentials locally and register only Operational Account Data with the backend: an opaque Mailbox Connection identifier, provider name, trusted device, and connection verification timestamps. Gmail account identifiers and email addresses remain inside the end-to-end encrypted Mailbox Connection definition and are not backend-readable. To route future Gmail pushes, registration also stores a backend-keyed digest of the canonical Gmail address mapped to that opaque connection identifier and its trusted devices; the digest is not an account identifier or email address and cannot be used to recover one without the backend key. Gmail push payloads are the narrow exception: Google supplies an email address and history identifier to the backend as transient Minimal Push Metadata; handlers derive the routing digest, route the wakeup, must not persist the payload values or include them in application logs, and discard them afterward. Backend APIs for Gmail connection status must not accept or return access tokens, refresh tokens, message bodies, categories, classification data, Gmail account identifiers, or email addresses.

The existing single-Gmail bootstrap implementation still stores and returns `emailAddress` and `providerAccountIdentifier` from `mailProviderConnections`. That temporary implementation does not meet this ADR and must migrate those fields into the encrypted Mailbox Connection definition before the multi-connection architecture is considered implemented; new connection-status APIs follow the boundary above.
