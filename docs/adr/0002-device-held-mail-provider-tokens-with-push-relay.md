# Device-held mail provider tokens with push relay

The product needs push and sync behavior but should keep mail provider OAuth tokens on trusted user devices for v1. The backend may receive minimal mailbox-change metadata from provider push systems and route wakeups to devices through APNs, but it must not fetch mail, hold provider tokens, read message bodies, read categories, or perform classification. This preserves the privacy boundary while accepting more complex client-side sync, watch renewal, and background execution constraints.

For Gmail connection, trusted devices persist provider OAuth credentials locally and register only Operational Account Data with the backend: an opaque Mailbox Connection identifier, provider name, trusted device, and connection verification timestamps. Gmail account identifiers and email addresses remain inside the end-to-end encrypted Mailbox Connection definition and are not backend-readable. Before registration, the device obtains a Google OpenID Connect ID token for its locally held Gmail OAuth credential; the registration handler validates its signature, issuer, audience, expiry, and that `email_verified` is true, and accepts the transient canonical Gmail address only when it byte-for-byte matches the verified `email` claim. The address and token are never persisted or logged. Canonical Gmail address means the verified `email` claim, encoded as UTF-8 without application-level trimming, case folding, dot removal, plus-address removal, or `googlemail.com` rewriting. To route future Gmail pushes, the handler derives the base64url-without-padding encoding of `HMAC-SHA-256(routing-key-version || 0x00 || canonical-address)` with a backend-held, access-controlled routing key, immediately discards the address, and stores only that versioned digest mapped to the opaque connection identifier and its trusted devices. Implementations must share deterministic non-production test vectors for each routing-key version, including ordinary addresses and dot, plus-address, and `googlemail.com` variants, to prove those variants are not silently conflated. The digest is not an account identifier or email address and cannot be used to recover one without the backend key. Routing-key rotation creates and routes both the current and prior versioned digests until all active registrations are renewed, then deletes the prior mappings; key material is restricted to the registration and push-routing service and is never returned to clients or logs. Gmail push payloads are the same narrow exception: Google supplies an email address and history identifier to the backend as transient Minimal Push Metadata; handlers derive the routing digest, route the wakeup, must not persist the payload values or include them in application logs, and discard them afterward. When a Mailbox Connection is removed from all trusted devices, the backend atomically disables and deletes its digest mapping before removing device authorization, invalidates queued wakeups for that connection, and retains no digest tombstone. Backend APIs for Gmail connection status must not accept or return access tokens, refresh tokens, message bodies, categories, classification data, Gmail account identifiers, or email addresses.

The Gmail removal workflow commits its encrypted Product Sync removal tombstone before deleting the operational backend route. Each trusted device retains its device-local Gmail connection status as a cleanup retry marker until that mailbox's credentials, caches, metadata, push state, Pending Provider Actions, and Outbox attempts are cleared.

The operational Gmail registration path stores only an opaque connection identifier, a product-account-scoped keyed identity-binding digest, routing digest and version, trusted device, provider, and verification timestamps. The identity binding uses the separate, stable `GMAIL_IDENTITY_BINDING_KEY`, does not rotate with the routing key, prevents an opaque route from being rebound to a different verified Google identity across trusted devices, and is never returned to clients. Operators must retain that identity-binding key across routing-key rotations. Readable Gmail status stays in the device-local push-connection store and in the end-to-end encrypted Mailbox Connection definition. The legacy readable connect, list, and remove endpoints are retired. When a trusted device registers an operational route for a matching legacy row, the registration action deletes legacy email-address verification signals in bounded, committed batches before the final mutation reuses that row and atomically removes its readable Gmail fields.

Device APNs routes use a dedicated operational heartbeat record rather than adding high-churn state to the trusted-device record. Registration refreshes the heartbeat, while successful sign-out, APNs invalidation, and APNs token reuse clear both the route and its Gmail push proof immediately. A daily bounded reconciliation clears routes whose heartbeat has not been refreshed for 30 days; routes created before heartbeat records existed use their trusted-device `lastSeenAt` value once for backfill or expiry. This accepts that a dormant but still signed-in device can lose push delivery until its next activation re-registers the route, in exchange for eventual cleanup after an authenticated unregistration failure without persisting, reviving, or depending on an obsolete Product Account identity token. Reconciliation compares the heartbeat inside the same transaction that clears a route, so a concurrent registration wins through Convex transaction conflict handling and remains active.

The bootstrap implementation authenticates the trusted device before fetching and caching Google's public signing keys, validates each transient Google ID token signature locally, and then enforces the accepted issuer, configured iOS OAuth-client audience, expiry, `email_verified` claim, exact canonical email, and stable Google subject. A history proof records a separate ownership-verification timestamp, and routing requires that timestamp to remain newer than device proof invalidation. This deliberately fences every history-only proof created before mailbox ownership verification shipped: an existing device must refresh its Gmail watch proof before its route can receive another wakeup. Google ID tokens are excluded from the device's Keychain encoding, sent only to the verification action, and never written to Convex tables, returned to clients, added to APNs payloads, or included in application logs.
