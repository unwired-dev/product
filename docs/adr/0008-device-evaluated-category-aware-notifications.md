# Device-evaluated Category-Aware Notifications

Notification Rules are user-owned encrypted Product Sync data. The Apple client stores the global notification switch, category eligibility, and per-connection notification policy in one encrypted payload and decrypts them only on trusted devices. Convex stores the opaque payload identifier, ciphertext, nonce, and key version; it cannot read those preferences or use them to decide which devices receive wakeups.

Authenticated Notification Rule loads and saves refresh an account-scoped, device-only Keychain cache of that opaque encrypted payload. A background wake first attempts Product Sync and may decrypt the cached payload when remote loading fails, including when the stored Product Account identity token has expired. Foreground loads still surface authentication failures, a successful authenticated empty response clears stale cached rules, and no session means the background route remains fenced after sign-out. The cache uses after-first-unlock, this-device-only accessibility so system-granted background work can read it without making the rules portable or plaintext at rest.

Notification Rule saves prefer correctness over background availability. After encryption succeeds, the client clears the existing cache before attempting the conditional Product Sync mutation. If cache invalidation fails, the client aborts before contacting Product Sync and the unchanged remote rules and prior cache remain aligned. If the remote request fails, authentication has expired, or the outcome is otherwise uncertain, the cache stays empty so removed or changed rules cannot drive a later notification. A conditional conflict may repopulate the cache from the authoritative payload returned by Product Sync. After a confirmed save, caching the committed payload is best effort: a Keychain write failure leaves the cache empty without reporting the already-committed save as failed. Background availability is restored only when a later authenticated load, successful save, or authoritative conflict response successfully writes its payload to Keychain.

Successful authenticated categorization reads also refresh a separate account-scoped, device-only Keychain cache encrypted with Product Sync key material. It contains only the current Custom Category snapshot and 24-hour exact-normalized-sender Future Learning Signal entries; explicit absence replaces older category or sender state, and stale sender entries are discarded during refresh. Resetting learned sender signals deletes or versions their synchronized encrypted payloads, then clears or versions this cache before the next background categorization on that device. The cache contains no messages or bodies. Only the background Gmail wake path may use it after remote categorization reads fail. Missing, expired, corrupt, or sender-mismatched context leaves the message uncategorized, while foreground categorization remains network-authoritative. Product Account cleanup deletes this cache.

A provider-native push signal remains a content-free background wakeup. The receiving device first fetches recent mailbox changes with that **Mailbox Connection**'s device-held authorization and runs local System Categorization. It may schedule a visible local notification only for a newly observed, non-historical message when the decrypted global switch is enabled, the connection is not disabled by its policy, and the resulting Message Category is eligible. The notification's count-only, sender, sender-and-subject, or full-preview presentation follows the device-local lock-screen content-level preference; no notification content is sent to Convex.

Overlapping wakes for the same Gmail route coordinate at the Stable Provider Message Identity boundary. Before Durable Message Metadata is written, notification candidates are journaled device-locally with the Gmail history boundary that made them eligible. A wake retry merges journaled candidates with the current provider delta, so process termination after inbox persistence cannot silently turn new mail into pre-existing mail. Journal entries at or below the saved route watermark are ignored and removed opportunistically after advancement.

A process-local claim prevents two active tasks from scheduling the same notification concurrently, an in-flight claim prevents a competing task from advancing the route watermark, and a completed-delivery receipt remains device-local and durable until later wakes can safely skip that message. Cancellation or delivery failure releases the in-flight claim for retry. Completed receipts and eligibility remain scoped to the Product Account and provider mailbox across route renewal, so a replacement route can finish pending work without redelivering a notification that the previous route already scheduled. The platform still cannot atomically combine notification-center scheduling with receipt persistence; completed receipts provide the accepted duplicate-prevention boundary around that system API.

Notification Rules are empty by default. If local metadata cannot be read, rules cannot be decrypted, categorization produces Uncategorized State, local notification delivery fails, or the app has no safe background execution time remaining, category-aware processing fails closed.

The Apple client also provides a separate, device-local Generic Notification Fallback. It is disabled by default and scoped to the Product Account on that device. When enabled, the client may replace failed, incomplete, or out-of-time category-aware processing with a content-free visible notification. The fallback preference, Notification Rules, categories, and message content are never sent to Convex; backend wakeup and routing behavior remain unchanged.

The account UI lets users enable categories and then requests local alert authorization. Denied authorization does not expose rules or message data and leaves the encrypted preference available for later use if the user enables notifications in system settings.
