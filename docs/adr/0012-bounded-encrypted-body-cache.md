# Use local-first metadata and a bounded encrypted body cache

Refreshing a cached body during an explicit open preserves its current protected-set and pin metadata.

Mailbox views will read Durable Message Metadata from local persistence immediately while provider synchronization updates it in the background. A newly connected mailbox becomes usable after metadata for its newest 50 messages, or all provider-visible messages when fewer exist, arrives; resumable historical metadata backfill then paginates through the complete provider-visible history with separate progress, and body prefetch starts without delaying initial availability. Backfill pauses under low storage, low power, or network loss. At each synchronization reference instant, each Mailbox Connection selects at most 500 distinct messages combined across Inbox and Sent Mailbox whose applicable received or sent timestamp falls from that instant minus 30 days through that instant, inclusive. A message appearing in both roles counts once, uses the later applicable timestamp, and uses Stable Provider Message Identity as the deterministic tie-breaker. Recent bodies and bodies belonging to pinned Threads are admitted by evicting only eligible bodies outside the combined selected-recent and pinned-Thread protected set; they never evict one another during that selection, and refused bodies remain on-demand until a later synchronization finds space. Every non-Spam, non-Trash body in a pinned Thread remains eligible regardless of those selection cutoffs, subject to that same protected-set admission rule. Spam, Trash, attachments, embedded image parts, and older unpinned bodies remain on-demand. Gmail checks body-free Content-Type metadata before prefetch and fetches only single-part plain-text or HTML messages, falling back to the provider payload MIME type when the optional header is absent; an encrypted exclusion marker prevents unchanged multipart or attachment bodies from repeating that preflight on every synchronization while leaving explicit opens on demand, but the marker is refused rather than evicting a protected readable body. Gmail cache entries use a versioned encrypted payload that retains minimized readable text together with the original decoded HTML alternative when one exists. An explicit message open may additionally resolve only MIME image parts referenced by normalized `cid:` sources after sanitization; image-only CID HTML remains renderable, attachment subtrees are never searched for matching content IDs, and those bounded bytes remain presentation-scoped in memory and never enter the body cache. Forward controls remain disabled until the expanded message body is available and quote that in-memory text directly, so a refused best-effort cache write cannot make an already opened multipart message unforwardable. A cached entry whose cheap entity-aware precheck finds a possible CID reference is sanitized and parsed to decide whether an explicit online refresh is required; ordinary cached HTML skips that parse during body-selection scans. Malformed payloads are removed and fetched again. System Categorization receives only the minimized text. The encrypted body cache has a 500 MB device-wide hard limit and evicts eligible opened older non-pinned bodies first, then eligible non-pinned prefetched bodies, and finally least-recently-read pinned-Thread bodies; bodies in the current selected-recent and pinned protected set are not eviction candidates until a later selection no longer protects them, and Thread Pin metadata survives eviction. Small sidecar files hold eviction timestamps, retention flags, and an opaque body-file identifier so admission, access, and selection scans do not read every encrypted body; sidecars count toward the same hard limit, are matched to the identity of their body file so an interrupted replacement cannot leave trusted stale metadata, and an older cache entry is given a sidecar when a scan can reserve its bytes without changing the readable encrypted payload. Complete Drafts, including semantic documents, attachments, and inline images, use a separately encrypted 100 MB device-wide store that never evicts Drafts automatically; each synced Draft has an encrypted manifest plus independently encrypted, ordered document and asset chunks whose encoded payloads stay below Convex's 1 MB value limit, so a large Draft is never written as one Product Sync payload. When full, the client prevents saving additional Draft content until the user removes or shortens a Draft, while incoming synced Draft content that would exceed the local limit remains encrypted in Product Sync and is marked pending local storage until space is freed. This supersedes ADR-0005's on-demand-only body-fetch policy, trading additional device storage and background work for fast list rendering, faster message opening, and bounded offline reading.

Opened body text retained solely for forwarding uses a 5 MB least-recently-opened memory bound and is cleared with the mailbox view model.
