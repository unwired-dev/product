# Classification engine interface

The Apple client will place email categorization behind a local Classification Engine interface rather than binding product logic directly to one Apple on-device AI API. Apple on-device AI is the preferred implementation, but the interface allows rule-based, platform-version-specific, or local model fallbacks while preserving the same output contract and keeping category immutability outside the classifier.

The first implementation is a deterministic local rule-based engine. Provider metadata sync sends available subject, snippet, and selected headers as Minimized Classification Input. The engine explicitly requests body text when metadata is insufficient; only then may the categorization service read an existing entry from the **Bounded Encrypted Body Cache**. Categorization never fetches a missing body from any provider, and classification or learning-signal load failures leave the message in Uncategorized State. Historical messages bypass the engine unless the user explicitly selects a bounded date range, using received timestamps for received messages and sent timestamps for sent messages, and already categorized messages always bypass it.

Assigned Message Category memberships are encrypted on device and written to Product Sync using an opaque payload identifier derived from the Mailbox Connection and Stable Provider Message Identity. A synced membership set is loaded before local classification so another trusted device's existing membership remains immutable.

A user may add or remove any Message Category membership, including on Uncategorized historical mail. The encrypted membership records each Category's User Override state and, for received messages only, carries a Future Learning Signal derived from the message's From address; sent-message overrides never create a Future Learning Signal. The signal uses the later of the user-action time and the overridden message's provider timestamp as its lower bound, while a separate unclamped user-action timestamp orders repeated overrides for both the message and its sender. Trusted devices may use that signal when categorizing Uncategorized messages received later from the same sender, but System Categorization never applies it to messages received before the override or to messages that already have that Category. The newest override for each sender is stored in its own bounded encrypted payload, addressed by a keyed sender digest. Clients derive digests only for senders in the current eligible message batch and fetch those exact payloads in bounded requests, so they neither expose sender addresses, scan unrelated sender signals or per-message memberships, nor grow one unbounded index document. Clients update both per-message memberships and sender signals with optimistic version checks and bounded retries against newer ciphertext, preserving unrelated concurrent sender updates and the newest membership for an overlapping sender while surfacing sustained contention as a typed sync error. Reapplying the same Category membership preserves its original learning-signal lower bound regardless of trusted-device write order; changing membership establishes a new lower bound. User Override state and learning data remain inside end-to-end encrypted payloads; the backend continues to store only opaque ciphertext and identifiers.

The Category Conflict Rule is enforced on trusted devices after decrypting competing membership sets. Atomic create-if-absent writes keep the first System Categorization for the same Category when devices classify the same message before sync converges. A User Override replaces a System Categorization for that Category regardless of arrival order. Concurrent changes to different Categories merge. When a conditional write reveals competing User Overrides for the same Category, concurrent removal wins over addition; otherwise every device converges on the first stored user action instead of falling back to last-write-wins. A later user action that begins after observing the prior override can still replace it and is ordered by its user-action timestamp. The backend participates only through opaque conditional writes and cannot inspect assignment sources, timestamps, or categories.
