# Accept best-effort background mail freshness

Mailbox credentials will remain device-local, so provider-native push signals may pass through the Minimal Push Metadata relay but trusted devices remain responsible for fetching and reconciling mail. Gmail and future Microsoft adapters will use provider push where available; generic IMAP will use an active connection while possible plus foreground and system-scheduled background refresh. Every authorized connection also synchronizes on app launch and foreground activation, uses a five-minute active-app fallback poll, supports manual refresh, and writes into locally observed mailbox data. Gmail recent reconciliation takes priority over Historical Metadata Backfill for the same connection: an active, current wake cooperatively cancels the backfill, waits for that operation to leave the per-connection gate, and only then writes recent metadata, preserving the last durable backfill checkpoint without overlapping writes. The preemption request remains visible while it waits so a backfill that has just become the lock owner cannot miss cancellation. The route persistence fence is rechecked inside the preemption gate immediately before cancellation. A wake that is already cancelled or whose persistence fence is stale does not preempt useful work, its provisional status does not supersede an untouched backfill completion but prevents cancellation or failure from restoring an older visible status, beginning preemption advances the completion fence so a successful backfill cannot overwrite the active push status, cancellation is checked again after gate ownership and after a backfill page returns, queued all-connection cleanup retains its FIFO position ahead of later per-connection wakes, and a backfill completion changes freshness state only when no newer superseding external sync status has been recorded and its connection authorization generation is still current. Direct caller cancellation restores the backfill's prior freshness status when no newer external sync has superseded it. A completed, cancelled, or externally fenced failed backfill requests a non-superseding mailbox reload because a page write can become durable before completion, cancellation, or failure is observed. A Settings row refresh marks its own reload notification as non-superseding and does not advance the external-status fence, so it cannot suppress the terminal state of the backfill it started. If a final backfill page becomes durable just before a recent sync cancels it and that sync then fails or is cancelled while acquiring the connection gate, the preemptor reacquires the gate, reloads the completed state, and reconciles pending actions; a failed recent sync that did not cancel an active backfill does not reconcile potentially stale cached metadata. Because Apple does not guarantee background task or silent-push execution and IMAP real-time updates require an active connection, the product accepts delayed background updates and guarantees reconciliation on the next available wake or foreground activation rather than operating a credential-holding backend mail service. See [Apple's background strategy guidance](https://developer.apple.com/documentation/backgroundtasks/choosing-background-strategies-for-your-app), [Apple's background push guidance](https://developer.apple.com/documentation/usernotifications/pushing-background-updates-to-your-app), and [RFC 2177](https://www.rfc-editor.org/info/rfc2177/).
