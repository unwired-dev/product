# Revoke devices with Product Sync key rotation

Revoking a Trusted Device immediately denies it access to Product Account APIs and push routing, then starts Product Sync key rotation for the remaining trusted devices so the revoked device cannot decrypt future synchronized changes. Revocation remains incomplete if rotation stalls or fails. It completes only after a new key epoch is durably committed and every remaining Trusted Device has fenced on that epoch; new ciphertext must use that epoch, so the old key cannot protect it. A revoked app that reconnects receives only a revocation rejection/tombstone that instructs it to delete the revoked Trusted Device Credential from device-only Keychain storage and purge local product data and mailbox credentials; that response grants no Product Account API access and carries no account data. Foreground activation revalidates the Trusted Device so an app that stayed running while offline follows the same purge path on reconnect. Queued Gmail and Microsoft Graph push wakes and scheduled Graph subscription renewal also revalidate before provider dispatch; a structured revocation fences the dispatch and schedules the same local session purge after the current background wake leaves its coordination gate. Each updated Apple client requests a random Trusted Device Credential when it first connects, stores that credential in device-only Keychain material, and presents it with every Product Account, Product Sync, and push-relay request. Routine reconnects present and preserve the existing valid credential so they do not invalidate concurrent in-flight requests; a missing or stale credential is replaced. The backend stores only its digest and verifies the Trusted Device Credential as well as Product Account ownership. Neither a Trusted Device ID nor an Apple identity token alone authenticates a device, and substituting a surviving ID cannot restore a revoked Trusted Device Credential's access. Issuing the first Trusted Device Credential activates account-wide enforcement; legacy devices must reconnect with an updated client, while accounts that have not activated credentials retain their existing access only until their first revocation. Once an account has a revocation tombstone, the backend also rejects registration under previously unseen client identifiers while preserving registration history so known non-revoked devices can reconnect after signing out. The app purges before any later provider access or synchronization. The product does not claim that remote revocation can erase data already copied from an offline or compromised device. Because mailbox credentials are device-local and belong to the Mail Provider, Settings also directs the user to revoke provider authorization separately when those credentials may be compromised.

The backend fences Product Sync reads by Trusted Device ID and accepts writes only at the pending or committed key epoch. Rotation distributes an opaque transition encrypted with the prior epoch only to remaining Trusted Devices. The transition carries the new account-key ring directly, so a remaining device can adopt it even when another device replaced the account Recovery Key; that device keeps its local Recovery Key and rewraps the adopted ring locally. Each device persists the new key before acknowledging it; retries adopt the backend's authoritative transition rather than generating another key. Sign-out reconciles that authoritative state and may proceed before the Recovery Key wrapper advances only when the pending epoch exactly matches the device's persisted local epoch and no Recovery Key remains unacknowledged. Revoking any device during an active rotation supersedes that transition with a fresh epoch before continuing: the replacement envelope is encrypted with the last committed key, carries the complete intermediate and legacy key ring, and becomes fetchable only after the target's API access is removed. Devices still on the committed epoch can advance directly, devices that already adopted the superseded epoch decrypt with their retained committed key, and a target that fetched or acknowledged the superseded epoch never receives the fresh key. Signing out an unacknowledged device still removes it from the acknowledgement set, preventing a lost device from deadlocking completion. The Recovery Key wrapper advances only after every remaining device acknowledges and contains the current key plus legacy epochs, preserving recovery of older ciphertext without giving the revoked device access to future keys.
