# End-to-end encrypted product sync

An unacknowledged publication of the opaque Recovery Key wrapper leaves the corresponding Recovery Key and its exact encrypted wrapper identity in the device-only local Keychain and blocks sign-out across app launches until that matching key presentation is explicitly acknowledged. A rejected or superseded wrapper cannot make its preserved key appear current, and interactive sheet dismissal does not acknowledge the key.

The product uses its own account system and backend to sync product-owned email organization data across a user's Apple devices. We will make this sync end-to-end encrypted so the backend can transport and store synced data, but cannot read synced categories or message-category assignments. This preserves the privacy promise while accepting additional complexity in trusted device enrollment, account recovery, support, and sync conflict handling.

The first implementation slice stores Product Sync data in Convex only as opaque AES-GCM payload fields: nonce, ciphertext, authentication tag, schema version, key version, and an opaque payload identifier. The Apple client creates local account key material in Keychain, wraps that account key with a user-held Recovery Key, and can restore the account key only from that Recovery Key plus the wrapped account key payload. Product Account sign-in and backend account recovery do not produce decryptable Product Sync key material by themselves.

Recovery Key replacement requires recent Sign in with Apple authentication, enforced by an authenticated HTTP action that reads the validated raw Apple identity token before invoking a private mutation, and rewraps the existing account key with a newly generated Recovery Key. The client offers replacement even when the locally held Recovery Key is current, serializes replacement attempts, reveals, and sign-out per Product Account across active windows, refuses a new replacement while a prior key remains unacknowledged, saves the replacement locally before compare-and-set publishing the opaque wrapper, immediately restores the prior local material after a known compare-and-set rejection, and reconciles ambiguous transport failures against the authoritative wrapper. If both the write response and reconciliation read are lost, it retains and reveals the replacement so a committed wrapper cannot become an unseen secret; sign-out still requires the authoritative wrapper to match the current local Recovery Key material exactly. Every post-network local write is fenced on the initiating Product Account session, so a replacement task cannot recreate key material after sign-out clears it. A current locally held Recovery Key can be shown again only after recent authentication, so a crash after publication cannot strand the sole user-held key. The backend and support personnel never receive the Recovery Key or decrypted account key.

When a device signs into an existing Product Account without local Product Sync key material, sign-in fetches the opaque recovery wrapper and requires the user to enter the matching Recovery Key instead of creating a new account key. Recovery completion refreshes Apple authentication before restoring local material and marking it initialized, so a delayed Recovery Key form cannot reuse an expired credential. Creating replacement account keys for existing accounts would make encrypted payloads unreadable across devices and could overwrite data with ciphertext protected by the wrong key. Product Sync record-writing paths must therefore require existing local key material even when the target record does not exist; they never bootstrap replacement keys. Sign-out verifies that the authoritative opaque recovery wrapper matches the current local Recovery Key material before preparing destructive local cleanup or deleting local Product Sync key material; accounts that have not backed up that exact Recovery Key must complete the backup first. It refreshes identity tokens that cannot safely cover the cleanup window, and every provider and Trusted Device cleanup uses that refreshed credential. A rejected recovery precondition keeps the valid session signed in and surfaces the error in account settings. Concurrent sign-out requests share one operation so cleanup and final state publication run exactly once.

Mailbox Connection definitions and the Default Sending Connection share one versioned encrypted Product Sync snapshot. The client updates that snapshot with compare-and-set writes and retries against concurrent trusted-device changes. Remove Mailbox Connection Everywhere retains an encrypted connection-scoped tombstone instead of deleting the record outright. Ordinary migration and reconciliation never overwrite a tombstone, so a device that was offline during removal cannot resurrect the connection when it next synchronizes; only a new, successfully verified provider authorization may explicitly recreate it.

Product-owned Pins use separate opaque Product Sync records keyed by a digest of the Mailbox Connection and Stable Thread Identity. The encrypted payload retains the full connection-scoped Thread identity and a pinned or unpinned state; unpins remain as tombstones. Each change carries a device-monotonic timestamp with the Trusted Device identity as a deterministic tie-break, so a delayed older change cannot overwrite a newer state. Compare-and-set retries are isolated to one Thread, so concurrent changes cannot overwrite Pins belonging to unrelated Mailbox Connections.

An internal typed encrypted-record boundary sits beside the existing domain-specific Product Sync services so later migrations can proceed incrementally without changing backend payloads. The Apple client owns typed encoding, encryption, decryption, and explicitly permitted device-local ciphertext fallback. The Convex TypeScript side owns only account- and Trusted-Device-scoped opaque ciphertext records; it must never decode or persist Product Sync plaintext. This preserves the privacy boundary by keeping plaintext and decryption keys off the backend while allowing the transport schema to remain stable. Singleton and record-family handles accept only `Codable` and `Sendable` values, return opaque revisions, bind AES-GCM associated data to the exact record identifier, and require existing device-local key material for every write. Updates serialize by Product Account and record identifier across suspended network work while leaving distinct records concurrent; conditional conflicts reload the authoritative ciphertext and let domain policy write again, accept it, or throw. Retries are cancellation-aware and stop after five conditional writes. Family listing follows Convex cursors, exact reads use bounded concurrent batches, and fixed cache policies keep authoritative reads, permitted ciphertext fallback, invalidation-before-write, and refresh-after-commit ordering inside the boundary.

Mailbox Connections, their authorization-generation ledger, and Pins now use this boundary directly. The two Mailbox Connection singletons are read in one typed exact batch so provider-access serialization and cache-fallback ordering remain unchanged; the boundary refreshes the encrypted local snapshot only after domain generation floors have been applied. Pins use the typed record-family interface while retaining their existing opaque digest identifiers, logical clocks, deterministic Trusted Device tie-break, tombstones, and decrypted identity validation. These services own only domain reconciliation decisions; associated data, codecs, key lookup, transport calls, conditional-write retries, and ciphertext-cache mechanics remain inside the shared boundary.
