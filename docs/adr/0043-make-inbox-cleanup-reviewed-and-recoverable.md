# Make Inbox Cleanup reviewed and recoverable

Inbox Cleanup will detect candidates on device and present a reviewable proposal rather than deleting mail automatically. The first-release eligibility predicate is the **Inbox Cleanup Candidate** definition in `CONTEXT.md`: a message must currently belong to Inbox, be read, be assigned the **Newsletters & Promotions** **System Category**, be older than 90 days, not belong to a **Thread** with a **Pin**, and have no reply evidence; the stated category and Spam or Trash exclusions also apply. A proposal selects individual **Inbox Cleanup Candidates**. The review UI may group candidates by **Thread**, but selecting that group expands to the individual eligible message identities and never enqueues a Thread-level action. The final action states how many messages will move to the Mail Provider's Trash; permanent erasure is outside this feature.

The Apple client owns detection, review, final revalidation, and enqueueing through the existing durable Provider Mail Action boundary. A Unified Inbox proposal may span Mailbox Connections and reports each connection's outcome without claiming a cross-provider transaction. Immediately before enqueueing, the client revalidates every selected candidate against the same eligibility predicate. If the eligible set changes, it returns to confirmation, identifies skipped messages, and displays the updated final Move to Trash count; only that reconfirmed set is enqueued. Each queued action records the selected message's **Stable Provider Message Identity** and is bound to its **Mailbox Connection**; a local database ID, Thread identity, or unscoped provider ID cannot identify the action. Immediately before provider mutation, execution revalidates that identity against the same eligibility predicate, cancels and reports candidates that changed, and moves only the unchanged eligible set to Trash. One proposal contains at most 500 messages, explains each group in plain language, and permits deselection; successful moves offer immediate Undo when supported, while provider Trash remains the longer recovery boundary. The TypeScript backend receives neither candidate content nor provider execution requests.

For an initial display, the card appears when one normalized sender mailbox address has at least ten eligible messages or the selected Inbox scope has at least fifty candidates. The sender key is the case-folded RFC 5322 `addr-spec` parsed from the `From` header after removing display-name and comment formatting; aggregation never crosses the selected Mailbox Connection Inbox or Unified Inbox scope. Not Now records a 30-day cooldown in Inbox Cleanup's **Feature Suggestion Preference** for the same Product Account and selected Inbox scope: either one Mailbox Connection's Inbox or the Unified Inbox selection. The Apple client computes the local baseline from the total eligible candidate count in that scope and owns every preference transition. The card may return early when the current eligible count for the same scope reaches at least twice that baseline, even when the doubled count is below the initial 50-candidate threshold. Showing the doubled-count card consumes that early-return eligibility: before rendering it, the client records the display time as the new cooldown start and the current eligible count as the new baseline, so the same candidate set cannot repeatedly display the card. It may next appear when that new cooldown expires or the eligible count doubles again; a later Not Now replaces both values. The TypeScript backend only transports or stores the opaque end-to-end-encrypted preference data, and neither candidate content nor message identities cross that boundary. The first release keeps these thresholds fixed and exposes enablement and suppression settings rather than speculative rule tuning.
