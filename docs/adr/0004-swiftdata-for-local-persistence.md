# SwiftData for local persistence

The Apple client will use SwiftData first for local persistence because the product should stay Apple-native and define models in Swift code rather than writing SQL schemas. This favors developer speed, SwiftUI integration, and minimal external dependencies, while accepting that advanced migrations, encryption strategy, sync-engine internals, and cache behavior may need careful validation as the mailbox model grows.

Gmail Durable Message Metadata is represented by connection-scoped SwiftData records containing the locally encoded metadata value, never a message body. Each record also retains derived Inbox visibility and provider Thread identity so opening the Inbox fetches and decodes only Inbox-visible Threads instead of the complete provider-visible archive; search and other mailbox views retain the full metadata set. A scoped read rebuilds at most one 500-record batch of missing derived indexes, while full-metadata synchronization or another full-metadata read completes any remaining upgrade work as it decodes those records. A separate connection-scoped checkpoint records the current full-scan generation and next Gmail page token. The newest 50 provider-visible messages establish Initial Mailbox Availability; subsequent pages are committed independently so cancellation, network loss, Low Power Mode, or process restart can resume without discarding usable metadata. A full scan marks prior records as reconciliation candidates, clears that marker as each provider-visible message is observed, and deletes the remaining candidates only with the final page. This preserves newly observed concurrent mail and prevents partial scans from turning unfinished pagination into deletion. Legacy file-backed Gmail metadata migrates on the first full-metadata load and is removed only after the SwiftData save succeeds.

Generic IMAP uses the same persistence shape with one backfill cursor and UIDVALIDITY value per provider mailbox. Stable message identity includes the connection, provider mailbox, UIDVALIDITY, and UID; a UIDVALIDITY change replaces only records from the affected mailbox. Each complete scan reconciles changed flags and expunges, while interrupted scans retain prior records until every mailbox backfill finishes.

On-premises Exchange EWS stores one connection-scoped, body-free SwiftData snapshot containing folders, message metadata, staged backfill offsets, and the identities observed by an in-progress full reconciliation scan. The newest 50 provider-visible messages per folder, or all of them if fewer, establish Initial Mailbox Availability; remaining local reconciliation candidates are deleted only once the scan reaches its final page, so interruption cannot turn an unfinished scan into local data loss.
