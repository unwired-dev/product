## Application cryptography

All application-owned encryption, key derivation, and keyed identifiers in the Apple clients use the system CryptoKit framework. The native `PrivateInbox` module performs these operations. The maintained JavaScript clients call that module and handle its opaque payloads. Their production mail logic has no independent JavaScript encryption implementation. Synthetic trusted-device code under testing is excluded from this production inventory.

The application defines its framing and account/device/record bindings. It does not implement or modify AES, GCM, HKDF, SHA-256, HMAC, X25519, ChaCha20, Poly1305, or HPKE internals. This statement concerns application source. Third-party libraries vendor upstream crypto source as described below.

## Network encryption and embedded TLS

The clients use system URLSession/Network/Security transport for HTTPS provider APIs, OAuth exchanges, Convex HTTP requests, and remote images. The isolated remote-content connection explicitly requires TLS 1.2, authenticates the original hostname, and uses `SecTrustEvaluateWithError`. Its source does not choose a cipher or curve. [RemoteContent.swift lines 345–374](https://github.com/unwired-dev/product/blob/fda18ae60afe034a5471ede54c13a29d2848014f/native/private-inbox/Sources/PrivateInbox/RemoteContent.swift#L345). System transport algorithms depend on the actual OS build and server negotiation.

IMAP and SMTP instead use SwiftMail revision `3b09f6e7de8273c19fb5c8f296cd2bdecc55c99e`, NIO SSL, and embedded BoringSSL. These connections are not OS-only encryption. The application explicitly selects `.fullVerification` and `.tlsv12`. IMAP uses implicit TLS. SMTP allows implicit TLS or required STARTTLS, with authentication after TLS. The person can select server, port, and SMTP transport, but cannot select algorithms/key sizes or lower the TLS floor. The current source does not implement ADR 0077's proposed certificate-pin override. [ImapMailbox.swift lines 154–160](https://github.com/unwired-dev/product/blob/fda18ae60afe034a5471ede54c13a29d2848014f/native/private-inbox/Sources/PrivateInbox/ImapMailbox.swift#L154), [SmtpMailbox.swift lines 60–72](https://github.com/unwired-dev/product/blob/fda18ae60afe034a5471ede54c13a29d2848014f/native/private-inbox/Sources/PrivateInbox/SmtpMailbox.swift#L60).

Its IMAP/SMTP connections create `NIOSSLClientHandler`. SwiftMail performs IMAP LOGIN or SMTP PLAIN/LOGIN inside TLS for password mailboxes. Mac's hybrid group is material to the inventory. ML-KEM-768 has a 1,184-byte encoded public key, 1,088-byte ciphertext, and 32-byte shared secret. The hybrid combines these with a 32-byte X25519 public value/shared secret. Client key share is 1,216 bytes, server key share 1,120 bytes, and the combined secret is 64 bytes before the TLS key schedule. It does not mean a 768-bit AES key. [Hybrid implementation](https://github.com/apple/swift-nio-ssl/blob/15e0b9e495786807272dd4891fa4bac76aa43034/Sources/CNIOBoringSSL/ssl/ssl_key_share.cc#L195), [ML-KEM constants](https://github.com/apple/swift-nio-ssl/blob/15e0b9e495786807272dd4891fa4bac76aa43034/Sources/CNIOBoringSSL/include/CNIOBoringSSL_mlkem.h#L49). ML-KEM internally uses SHA3-256, SHA3-512, SHAKE128, and SHAKE256. [Pinned ML-KEM hash functions](https://github.com/apple/swift-nio-ssl/blob/15e0b9e495786807272dd4891fa4bac76aa43034/Sources/CNIOBoringSSL/crypto/fipsmodule/mlkem/mlkem.cc.inc#L50). The library also contains ML-KEM-1024 and other capabilities that the application's default group list does not enable. Source proves the default offer, not that any observed mailbox negotiated it.

Both NIO SSL versions use this pre-TLS-1.3 cipher rule, unchanged by SwiftMail:

```text
ECDH+AESGCM:ECDH+CHACHA20:DH+AESGCM:DH+CHACHA20:ECDH+AES256:DH+AES256:ECDH+AES128:DH+AES:RSA+AESGCM:RSA+AES:!aNULL:!eNULL:!MD5
```

[Default rule](https://github.com/apple/swift-nio-ssl/blob/322f3c2a4a21df31c84ca416bf65ee5e9059e440/Sources/NIOSSL/TLSConfiguration.swift#L279). It permits AES-128/AES-256 GCM or CBC, and ChaCha20-Poly1305, with supported ECDHE/RSA choices. CBC suites can use HMAC-SHA-1 or HMAC-SHA-256. GCM/ChaCha suites use AEAD and SHA-256/SHA-384 handshake derivation. `!MD5` excludes MD5 cipher MACs; it does not remove every MD5/SHA-1 implementation from the library. BoringSSL's table does not implement finite-field DHE cipher suites despite the broad `DH` aliases in the rule. TLS PSK callbacks and a client identity certificate are not configured. [Implemented cipher table](https://github.com/apple/swift-nio-ssl/blob/322f3c2a4a21df31c84ca416bf65ee5e9059e440/Sources/CNIOBoringSSL/ssl/ssl_cipher.cc#L50), [client defaults](https://github.com/apple/swift-nio-ssl/blob/322f3c2a4a21df31c84ca416bf65ee5e9059e440/Sources/NIOSSL/TLSConfiguration.swift#L648).

The available TLS 1.3 suites are `TLS_AES_128_GCM_SHA256`, `TLS_AES_256_GCM_SHA384`, and `TLS_CHACHA20_POLY1305_SHA256`. AES keys are 128 or 256 bits, ChaCha keys 256 bits, AEAD tags 128 bits. Default preference depends on AES hardware support. [iOS handshake_client.cc lines 105–137](https://github.com/apple/swift-nio-ssl/blob/322f3c2a4a21df31c84ca416bf65ee5e9059e440/Sources/CNIOBoringSSL/ssl/handshake_client.cc#L105), [Mac ssl_cipher.cc lines 1282–1318](https://github.com/apple/swift-nio-ssl/blob/15e0b9e495786807272dd4891fa4bac76aa43034/Sources/CNIOBoringSSL/ssl/ssl_cipher.cc#L1282).

BoringSSL's default peer-signature list permits ECDSA P-256/SHA-256 and P-384/SHA-384, RSA-PSS with SHA-256/384/512, RSA PKCS#1 with SHA-256/384/512, and legacy RSA PKCS#1/SHA-1. Actual certificate RSA modulus length and signature depend on the server certificate and trust validation. The app does not supply one fixed RSA key size. Library support tables contain additional signature types, including Ed25519, but those are not proof they appear in the default verification offer. [iOS default verification list](https://github.com/apple/swift-nio-ssl/blob/322f3c2a4a21df31c84ca416bf65ee5e9059e440/Sources/CNIOBoringSSL/ssl/extensions.cc#L288), [Mac default verification list](https://github.com/apple/swift-nio-ssl/blob/15e0b9e495786807272dd4891fa4bac76aa43034/Sources/CNIOBoringSSL/ssl/extensions.cc#L284).

Transport keys are ephemeral/session state managed by system TLS or BoringSSL. No application TLS key export, custom cipher UI, custom group setting, PSK callback, key-log callback, renegotiation enablement, or client private-key configuration is present. ## Configurability and standards

End users cannot choose the data-encryption algorithm, key size, KDF, HPKE suite, nonce, crypto library, or TLS cipher list. Users can supply a Recovery Key, transfer an Enrollment Code, approve/revoke devices, connect mailboxes, choose implicit SMTP TLS or STARTTLS, and remove cached data. Those operations use fixed cryptographic constructions. Operators configure server authentication/routing secrets and distribution. Ordinary source modification can change the code, but the shipped product exposes no general-purpose encryption API or algorithm selection UI.

The following primary references identify constructions and API semantics. They do not certify this implementation or settle a country's legal classification:

- [NIST SP 800-38D](https://csrc.nist.gov/pubs/sp/800/38/d/final) specifies GCM authenticated encryption. [CryptoKit AES-GCM seal](<https://developer.apple.com/documentation/cryptokit/aes/gcm/seal(_:using:nonce:authenticating:)>) documents automatic nonce generation; [nonce initialization](<https://developer.apple.com/documentation/cryptokit/aes/gcm/nonce/init()>) specifies 12 random bytes.
- [RFC 5869](https://www.rfc-editor.org/rfc/rfc5869.html) defines HKDF. [RFC 9180 sections 5 and 7](https://www.rfc-editor.org/rfc/rfc9180.html) define HPKE base/PSK modes and the selected X25519/HKDF-SHA-256/ChaCha20-Poly1305 suite sizes. It is an IRTF Informational RFC, not an Internet Standards Track RFC. [Apple's suite documentation](https://developer.apple.com/documentation/cryptokit/hpke/ciphersuite/curve25519_sha256_chachapoly) and [PSK sender initializer](<https://developer.apple.com/documentation/cryptokit/hpke/sender/init(recipientkey:ciphersuite:info:presharedkey:presharedkeyidentifier:)>) match the actual calls. Local iOS/macOS 27 CryptoKit SDK interfaces were also inspected and hashed.
- [RFC 8446](https://www.rfc-editor.org/rfc/rfc8446.html) specifies TLS 1.3. [NIST FIPS 203](https://csrc.nist.gov/pubs/fips/203/final) specifies ML-KEM. [RFC 10024](https://www.rfc-editor.org/rfc/rfc10024.html) identifies the hybrid TLS group used by the Mac vendor source. This is separate from the application HPKE suite, which uses X25519 without ML-KEM.
- [RFC 6455 section 4.2.2](https://www.rfc-editor.org/rfc/rfc6455.html#section-4.2.2) explains WebSocket SHA-1 accept processing. [RFC 9562 section 5.5](https://www.rfc-editor.org/rfc/rfc9562.html#name-uuid-version-5) defines SHA-1 UUIDv5.
- [Apple's export documentation table](https://developer.apple.com/help/app-store-connect/reference/app-information/export-compliance-documentation-for-encryption/) distinguishes standard implementations outside the OS from OS-only encryption and includes a France documentation route. The embedded NIO SSL/BoringSSL path makes an OS-only description technically inaccurate. It does not by itself determine an exemption, classification, or declaration answer.
