Apply every section of `.opencodereview/rules/common.md` to this file first; read it now if it is not in context, and apply its R11 in full. The rules below add the defects specific to Markdown, changesets and the review-rule files under `.opencodereview/`.

Documentation here is product truth that agents execute: an implementer follows the operational guides literally, and the reviewer treats ADRs and architecture companions as authority. A wrong sentence becomes wrong code.

#### Accuracy against the repository

- A command, script name, path, flag, version or environment variable that does not exist as written. Check it against `package.json`, the workflow files and the tree.
- A GitHub environment setup or recovery snippet in `docs/convex-deploy.md` or another operational guide that claims a branch-only secret boundary but only enables custom-policy mode and adds the allowed branch. Existing branch or tag policies survive those calls; verify that recreation or explicit policy deletion removes every unwanted policy before storing secrets, and that recreation restores deleted secrets. Otherwise a stale allowed ref can run its own workflow definition with deployment credentials.
- A CLI setup example in `docs/convex-deploy.md` or another operational guide that omits required arguments, assumes the wrong working directory or leaves an input-reading command without a documented value, file, pipe or interactive step. Check the installed CLI's help, package context, deployment selector and input behavior; otherwise following the example can fail or wait for unspecified stdin rather than configure the intended setting.
- A deployment setup guide treating every variable in a mixed root `.env.example` as a backend input. In `docs/convex-deploy.md`, check deployment variables against `packages/convex/convex/convex.config.ts` and keep local deployment selectors and host build settings at their owning boundary; otherwise operators configure the wrong environment. Link the backend schema rather than copying its variable list.
- Behavior described as shipped that the code does not implement, or planned replacement behavior stated in the present tense. Unavailable or deferred checks are described as deferred.
- `DESIGN.md` or another interface design guide omitting or contradicting observable contracts in `docs/product/` or the owning feature guides in `docs/`. Sweep every described screen and component's layout, recipes, controls, states, behavior, defaults and counts against the applicable requirements and topic glossaries after scope and supersession checks; do not stop at the reported defect or changed sentence. Trace preference-controlled visual elements and glossary-defined component contracts, including contact images, Category badges, attachment indicators and Response Assistance choices. Check assistance-marker acceptance, saved list density, sidebar hierarchy, connection-local status, Cc/Bcc disclosure, message-versus-Thread action targets in the reader and Catch Up, Mail View configuration and badges, and composer controls including Translate beside Rewrite. Reconcile an authorized requirement change with every guide stating the same behavior, distinguishing its target layout from current implementation. Keep visual guidance and required elements explicit; link to owning contracts for lifecycle, fallback, persistence and delivery details instead of copying them. Distinguish mockup dimensions from requirements and flag maintainer-approved departures pending reconciliation. Otherwise following the guide can change behavior, omit controls or target the wrong messages.
- Selected or unread states in `DESIGN.md` or another interface design guide relying on hue alone or an insufficient lightness difference. Check the state recipe and component description together for an additional visual distinction, such as an emphasized label or the sufficient lightness contrast or foreground/background inversion described by [WCAG Use of Color](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html), and verify text/icon contrast against the composited Light and Dark surfaces; otherwise documented contrast pairings can pass while a navigation state remains indistinguishable.
- A provider-scope amendment in `docs/product/power-user-launch.md` or an ADR that leaves `docs/google-registration.md`, `docs/apple-registration.md` or another operational first-use guide requiring a superseded provider. Trace every launch Product Sign-In through device admission, provider choice, verified first connection, cancellation, retry and relaunch; distinguish current implementation/evidence from launch requirements. Otherwise a promoted provider remains unreachable as the first mailbox despite appearing in the launch list.
- Linked assessments in `docs/research/`, such as `blocknote.md` and `editor-alternatives.md`, prescribing incompatible initial evaluations or fallback conditions. Compare their recommendations and proposed next steps with the authorized evaluation scope; identify the governing recommendation and qualify superseded or conditional plans in each report. Otherwise readers can spend the first prototype effort on the wrong candidate or mistake a comparison baseline for an approved work item.
- Composer replacement gates in `docs/research/blocknote.md`, `docs/research/editor-alternatives.md` or a linked evaluation plan omitting required native text behavior, host presentation contracts or performance pass/fail criteria. Trace spelling, autocorrection and predictive text to the authored-body contract, and timing, next-frame feedback, stall caps and reference-device scope to the current replacement verification targets and applicable ADRs 0018/0025. Trace host gates to current Draft behavior and applicable ADR 0057: content-growing body in one outer scroll and preserved Draft/document/selection/focus/undo/autosave through applicable adaptive and collapsed/expanded transitions. Check scope and supersession first; do not impose prototype overlay geometry on every replacement host. Otherwise a browser candidate can pass generic focus/resize measurements while violating its applicable composer contract.
- Composer requirement inventories or fidelity/native-journey gates in those reports or their linked evaluation plans replacing the canonical authored-body contract with an incomplete summary. Compare the full current contract in `docs/product/messages-and-delivery.md`, `docs/drafts.md`, `docs/draft-assistance.md`, `docs/message-translation.md` and applicable ADR 0025 after supersession checks. Trace link editing and reopening, Slash Command Menu interaction, image paste/drop versus picker representation and explicit conversion in both directions, and word-sized Undo/Redo with each activation advancing even before redraw. Exercise accepted rewrites, reply suggestions and Draft translations through the native bridge as single undoable edits, checking captured scope, formatting, excluded content and save/reopen; stale-result rejection alone does not prove successful application. Require the canonical contract as acceptance authority and exercise these interaction paths; distinguish deferred implementation from required qualification. Otherwise a candidate can pass while losing authored semantics or required commands.
- A feature specification in `docs/*.md` with undefined first-use state or interaction targets, or conflicting with its owning requirements, general rules or exceptions. Trace reused behavior to `docs/product/` or its feature guide, check scope and explicit supersessions, and qualify rules or cross-reference exceptions; otherwise implementers invent behavior or receive incompatible contracts. Preserve existing behavior or report the conflict for an authorized decision.
- A Mail Commitments amendment that updates a feature brief but leaves the owning `On-Device Mail Assistance`, `Remove Mailbox Connection Everywhere` or `Return-to-Attention` definition in `docs/domain/` incompatible with it. Trace the exception through the canonical definition, product requirements and applicable ADR, preserving other assistance and cleanup boundaries; otherwise an implementer can reject authorized scanning, erase accepted records or bypass the shared attention preference.
- An automatic-scanning amendment in `docs/product/mail-commitments.md` that defines fresh consent but leaves already-enabled assistance, prior scan Off or master-Off/re-enable transitions undefined. Enumerate each device/Profile's legacy and informed consent and saved scan choice, including declined confirmation, upgrades and the start boundary. Trace deliberate master Off separately from scan Off and involuntary system/model interruption, including cancellation, late pre-Off results after re-enable, delayed delivery and newly downloaded history. Preserving a setting alone does not specify the admitted mail interval. Check the owning assistance guides and ticket acceptance criteria; otherwise old consent silently authorizes expanded analysis, an explicit Off is reset or disabled history is implicitly scanned.
- A Profile Lock exception in `docs/product/mail-commitments.md` or `docs/product/assistance.md` that preserves saved proposals but weakens cancellation into pausing or resumable work. Compare the transition verbs directly with ADR 0072 and the owning assistance contract, including an in-flight result delivered after unlock. Require cancellation, permanent rejection of pre-lock results and current consent/scan/source checks for new work; otherwise a persistence exception can publish private analysis from an invalidated task after reauthentication.
- A Mail Commitment Profile-move contract that covers accepted records but omits unaccepted output or minimal per-source acceptance/dismissal/deletion decisions. Enumerate old and target ownership, single/mixed sources, cancellation, interruption, delayed device observation and late work against `docs/product/mail-commitments.md` and ADR 0072. Verify proposal retirement without output transfer, source-partitioned suppression without foreign content, authoritative deletion fences and the target's consent/scan gates before publication or acceptance; otherwise moves expose another Profile's sources, lose human suppression or resurrect deleted records.
- A Mail Commitment Profile-move contract in `docs/product/mail-commitments.md` that reassigns the accepted record but leaves already-scheduled reminder work with the old Profile's owner or controls. Trace sole-source and reviewed mixed-source ownership changes through the canonical move outcome, ADR 0072 and reminder ticket criteria. Require preservation of the configured time, current notification ownership, known obsolete alert reconciliation and target privacy/attention controls before delivery. Check cancellation, interruption/retry, same/different device owners, disabled/quiet/locked targets, offline observation and current-state tap routing without promising cancellation on an unreachable device or selecting a new scheduler algorithm. Otherwise record ownership can be correct while obsolete or duplicate alerts reveal content or interrupt the wrong Profile.
- A synchronized Mail Commitment review decision in `docs/product/mail-commitments.md` that constrains only future scans, leaving a matching persisted proposal, open review or in-flight acceptance/result actionable. Trace decision and target-record arrival in both orders, delayed offline observation and current Profile ownership against ADR 0072. Require retirement and known-state reconciliation before display, acceptance and publication, without foreign links or duplicate creation while a record is pending. Check a distinct obligation from the same message and a fresh update to an accepted target remain reviewable; an entire Thread, source or target is not the reviewed-proposal identity. Otherwise synchronization can repeat a reviewed obligation or broad suppression can discard unrelated work. Compare actual transition operations to authority; a decision map or matrix row alone does not prove this contract.
- A deletion contract in `docs/product/mail-commitments.md` or ADR 0072 that promises removal while its general conflict-preservation rule can recreate deleted authored content. Check concurrent/stale edits, scans, retries and conflict copies against explicit Delete precedence, with only the authorized minimal encrypted review decision retained; otherwise synchronization can resurrect private content after deletion.
- A Mail Commitment owner-deletion contract that names accepted records but omits device-local model output or scan state. Compare Profile-only and whole-account removal with persisted/open queues, active/interrupted scans, late callbacks, retry, relaunch, unlock and owner recreation in the product contract and ADR 0072. Require observing devices to cancel/fence affected work and physically purge the affected proposals and scan state without restoring prior permission or touching unrelated scopes. Preserve offline observation and native purge versus TypeScript invalidation ownership; otherwise removed private content or consent can return.
- A Mail Commitment close/reopen contract that leaves already-scheduled reminders active after observed Done/Cancelled or revives obsolete work on Reopen. Trace known schedules, queued/late delivery, current ownership/revision and controls, future/past chosen times, explicit reminder edits/removal and delayed synchronized reopening against the panel-selected product contract and ADR 0072. Require closed-state retirement/fencing and restoration only of a still-current configured future choice on explicit Reopen; past times never cause immediate catch-up, and superseded/removed times never rearm. Preserve the offline stale-alert limit and Delete precedence; otherwise closed work interrupts or a reopened item uses obsolete authorization.
- A source-removal exception in `docs/product/mail-commitments.md` that documents retained authored state but leaves its pre-confirmation disclosure only in reviewer-owned authority or omits a retained field. Compare every retained field against the record definition: I owe/Waiting for direction is distinct from Open/Done/Cancelled lifecycle state, and retained reminder configuration is distinct from active scheduled work. Trace the removal decision, cancellation and locked Profile through the implementer-facing contract, owning decision and ticket criteria. Require disclosure of retained app/Private Sync state, purged sources/proposals, unavailable links and the existing Delete versus Profile/account purge choices without protected content; otherwise removal can retain private text without informed notice or discard part of the reviewed record. Do not add an unapproved bulk-delete action.
- A cross-device Mail Commitment acceptance rule that retires pending queues but never reconciles records independently authored before either device learned the other's decision. Start with both queues gone, then reconnect in both orders with retries, independent/conflicting edits, completion/deletion and retained route/reminder references. Require the approved one-logical-record convergence without resurrecting deleted content, silently reopening completed state or exposing foreign-Profile sources. Preserve distinct obligations, fresh update proposals and separately authored manual records sharing correspondence; do not select an unapproved matching/storage algorithm or merge UI. Otherwise queue suppression can pass while duplicate commitments and obsolete reminders remain.
- A deadline contract in `docs/product/mail-commitments.md` that requires a chosen zone but leaves first-use selection, ownership or synchronization undefined. Check the visible editable new-manual-deadline default, the confirmed per-commitment zone, source-message anchoring and stability through travel/device changes against the accepted decision; otherwise devices can reinterpret the same deadline or introduce an unapproved global preference.
- An accepted Mail Commitment update treated as available merely because its earlier target exists. In `docs/product/mail-commitments.md`, compare decision-before-outcome and outcome-before-decision delivery against current authoritative state, including newer authored edits, completion/Delete, owner loss and reminder revisions. Require pending status for unavailable accepted changes without labelling stale fields as accepted, reviving a retired proposal, blocking an otherwise usable manual target or exposing another Profile. Incorporation, supersession or resolution by current state does not require retaining/restoring literal old revision bytes; otherwise reordered sync presents stale changes or overrides newer authority. This adds no model-proposed reminder or wire/history protocol.
- A user-chosen Mail Commitment reminder time whose temporal semantics are inferred from deadline rules. Trace its visible editable initial zone, confirmed fixed instant/zone, encrypted synchronization and independence from deadline zone through travel, different notification owners, Profile moves, close/Reopen, explicit edits and daylight-saving boundaries against ADR 0072. Preserve current future-only configured-reminder eligibility, Delete/removal authority and past-time no-catch-up without promising exact delivery or selecting a scheduler; otherwise reassignment can silently shift a chosen interruption or restore an obsolete one.
- A Mail Commitment reminder contract or shared `Return-to-Attention` summary that omits Return-to-Attention, Quiet State or Quiet Hours. Trace every applicable interruption constraint to `docs/domain/privacy-and-sync.md` and the owning notification requirements while retaining Profile Lock, system authorization and content policy; otherwise commitment reminders can interrupt a Profile that has suppressed return prompts.
- In `docs/catch-up.md`, missing or conflicting first-use and no-unseen behavior, seen-state lifecycle, or bubble and reader contracts. Check durable device-local seen-marker initialization, ownership, retention, cleanup and independence from provider read state against ADR 0019. Trace message order, Thread-versus-message actions and collapsed-category exceptions to the owning reader and Catch Up requirements; otherwise implementers reset or share a divider, retain orphaned progress or act on the wrong messages.
- A storage or isolation boundary in `docs/drafts.md`, `docs/private-inbox-storage.md` or another feature guide that omits or misassigns Apple versus TypeScript responsibility for encryption/key custody, owner/revision refusal, limits or lifecycle cleanup. Trace the native enforcement and the shared-store caller separately, including purge execution versus in-memory invalidation; otherwise later changes can target the wrong layer and bypass a protection. For WebView composer gates in `docs/research/blocknote.md`, `docs/research/editor-alternatives.md` or a linked evaluation plan, require non-persistent browser storage and website-data inspection after teardown, relaunch and account removal; encrypted native saves alone do not rule out a second plaintext copy in browser storage. State the concise ownership requirement and link to the owning guide without copying implementation mechanisms or rationale.

  companion treating every credentialed-call reply as a non-secret projection,

#### Vocabulary

- A term from `GLOSSARY.md` or a topic glossary replaced by a synonym, a new domain term used without a definition, or a glossary entry changed outside `docs/agents/domain.md`'s policy.
- Product Sign-In, Trusted Device, Mailbox Connection and Private Sync used interchangeably; they are distinct and their difference carries privacy meaning.

#### Authority and placement

- A design instruction in `AGENTS.md`, `docs/agents/` or another workflow/guide that gives a stale frame priority over a product requirement or sends a conflict already resolved by documented authority to the decision panel. Check `DESIGN.md`'s authority statements and the owning product requirements or feature guides before following the frame or escalating. Preserve design follow-ups for stale frames and escalation for unresolved conflicts, missing states or scope changes; otherwise the workflow can override required behavior, controls or defaults or reopen an accepted decision.
- Architecture, design rationale or internal implementation mechanisms written into an implementer-facing file (`AGENTS.md`, `README.md`, `docs/*.md`, `docs/agents/`, `docs/product/`, `docs/domain/`). They belong in `docs/architecture/` or an ADR; the implementer-facing file keeps setup, commands, validation, observable behavior and concise boundary-ownership requirements that its implementer must satisfy.
- A requirement that exists only in a reviewer-only file after the change. The implementer must still be able to read every requirement it has to satisfy.
- An accepted ADR edited to reverse its decision without a supersession note, or a new decision recorded outside an ADR. Use the full ADR filename where numbers collide.
- A prototype, historical or archived statement presented as a first-release requirement or as qualification evidence.
- An agent guide (`AGENTS.md`, `docs/agents/`) that contradicts the root guide's workflow, validation or triage instructions, or that adds an always-loaded line which only restates a linked document.

#### Changesets

- A changeset or feature note that describes only the preferred mechanism while omitting an implemented fallback that weakens the stated guarantee. Trace the owning helper, such as `PrivateInboxStore.fullSync(_:)`, and its failure branches; otherwise consumers can mistake best-effort behavior for an unconditional durability or availability promise.
- A changeset naming a package outside the workspace, a bump level that understates the change (a breaking exported type or wire change marked `patch`), or a summary that does not say what a user or consumer observes.
- A runtime behavior or exported API or type change in the task with no changeset. Documentation, tests and internal refactors may omit one.

#### Review rules (`.opencodereview/`)

- A `rule.json` entry placed after a broader pattern that already matches its files; the first match wins and entries never combine.
- An `include` pattern whose representative owned files resolve to the fallback or an unrelated path rule, skipping the intended checks. Verify selection and resolution with the real CLI, preserving documented exceptions such as contract fixtures.
- A `rule` path that does not exist or is unreadable. OCR warns on stderr and silently applies no project rule to those files.
- A path rule whose first instruction no longer requires `rules/common.md`, or a change to `common.md` that drops a responsibility listed in `docs/architecture/open-code-review.md`.
- `merge_system_rule` changed for an entry without checking the resolved text with `ocr rules check <path>`; the embedded TypeScript rule contradicts the Effect conventions and is deliberately not merged for Effect-governed code.
- A rule bullet that a linter or type checker already decides, that names no file, helper or invariant, or that gives no consequence. Such bullets produce noise and dilute the rest.
- Validated review feedback or an escaped defect in the task with no rule change and no recorded reason for declining one; see R12.
- An `include` or `exclude` change that hides task-owned source from review or admits dependencies, build output, generated files or secrets.
